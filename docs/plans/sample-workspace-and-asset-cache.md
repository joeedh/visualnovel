# Sample workspace + generated-asset cache

Status: **shipped** — both halves: the seeded `examples/mySampleRepo` workspace and the
recorded asset corpus behind `makeProject({ assets: 'cached' })`.

Two changes that share one cause: **generated bytes are landing in the source tree.** A real
run of `examples/sample` put 112 MB of untracked output inside a directory whose tracked
contents are 13 KB, and there is no way for anyone else to obtain that art short of paying
for it again.

The fix has two halves, and they are independent enough to land separately:

- **A** — the desktop app stops writing into `examples/sample` and seeds its own scratch repo.
  `examples/sample` becomes a read-only template.
- **B** — a small, committed corpus of **real** generated assets that fixtures can populate
  from, with a defined staleness rule and a refresh path.

This supersedes the submodule idea in full. Nothing needs to be a submodule once the app
writes somewhere that is gitignored.

## Where the weight actually is

| | size | tracked today |
| --- | --- | --- |
| authored inputs (`project.yaml`, `characters/`, `locations/`, `screenplay/`, `AICONTEXT.md`, one skill) | **13 KB**, 8 files | yes |
| `vngen/build/assets` — 51 PNGs from the real run | **108 MB** (avg 2.12 MB, max 2.6 MB) | no |
| `vngen/work` (candidates, approved portraits, shot files, story graph) | 3.3 MB | 1 file |
| `vngen/state` (`tasks.jsonl`, reviews) | 124 KB | no |

The template is 13 KB. Everything heavy is output, and none of it has ever been committed.

## A · Seeded scratch workspace

### Today

`apps/desktop/src/main/index.ts:61`:

```ts
return process.env.VN_PROJECT ?? join(__dirname, '..', '..', '..', '..', 'examples', 'sample');
```

Launching the app runs the pipeline into the source tree. There is no separation between
"the sample we ship" and "the copy I have been messing with", so `git status` fills with
generated output and the only way to get a clean sample back is to delete files by hand.

### Proposed — **shipped** (`apps/desktop/src/main/workspace.ts`)

On startup, with no `VN_PROJECT`, resolve to **`examples/mySampleRepo`**. If that directory
does not exist:

1. Copy the authored inputs from `examples/sample` — as shipped, that is every entry except a
   deny-list (`vngen`, `keys`, `.git`, `node_modules`), so a new input file or skill is seeded
   without anyone remembering to add it. **Not `vngen/`**: a freshly seeded workspace has not
   been run, and pretending otherwise would make the first `run` look like a no-op.
2. `git init`, set a repo-local identity, commit the inputs as `Sample project inputs`.
3. Open it.

If the directory already exists, **open it untouched** — never re-copy, never overwrite. It
is the user's working copy and it is the only thing standing between a stray reseed and a
day's authoring. Resetting is `rm -rf examples/mySampleRepo`; that needs no code and cannot
misfire.

### Details that will otherwise bite

- **`examples/mySampleRepo` goes in `.gitignore`.** A nested repo inside an ignored directory
  is invisible to the parent — no submodule, no `gitlink` entry, no `--recursive` clone
  requirement. This is the entire reason the submodule question disappears.
- **A fresh repo has no committer identity.** `@vn/git` deliberately holds no policy, so
  testkit reached through a `GitInternals` cast to set `user.email` / `user.name` /
  `core.autocrlf`. A second consumer justified promoting that: **`Git.config(key, value)`**
  now exists — plumbing, not policy — and the cast is gone. Without a local identity,
  `git commit` fails outright on a clean box.
  Shipped with a companion **`Git.configGet(key)`**, because the app's workspace differs from
  testkit's temp dir in one way that matters: the user will keep authoring in it, so a global
  identity of theirs must not be stomped. Identity is filled in only when git can't already
  answer; `core.autocrlf false` is unconditional, being a repo requirement rather than a
  preference.
- **`core.autocrlf false`** matters here for the same reason it does in testkit: the branch
  editor asserts on byte-exact screenplay patches.
- **Packaged builds have no `examples/`.** `__dirname/../../../../examples` only resolves
  when running from the repo. That is already true today, so this plan does not regress it,
  but the seeding path should fall back to `app.getPath('userData')/mySampleRepo` when the
  repo-relative parent does not exist — otherwise the first packaged launch dies on `ENOENT`
  rather than on something legible.
- **`examples/sample` keeps its two hard references** and needs no changes:
  `packages/model/src/tests/branchpatch.test.ts:298` reads `script.fountain` at module load
  (a top-level `readFileSync` — a missing file fails the whole `@vn/model` suite, not one
  test), and the docs' `vngen run examples/sample` walkthrough.

### One-time migration

The 108 MB already on disk is real, paid-for art. Move
`examples/sample/vngen/` → `examples/mySampleRepo/vngen/` rather than deleting it: the
scratch repo then starts fully generated, and the art survives locally. This is a migration
step, not the code path — the seeding code still copies inputs only.

`examples/sample/vngen/work/story.graph.mmd` is tracked and stays; it is 2 KB of Mermaid and
the `vngen graph` walkthrough regenerates it.

### Docs this changes

CLAUDE.md states "`vngen/` is committed (it is the reproducible output of a run), not
gitignored." That policy still holds **for a user's own project**. It stops applying to
`examples/sample`, which becomes inputs-only. The sample-project and desktop-runner sections
both need to say which directory the app actually opens.

## B · Generated-asset cache

### What it is for — and what it is not for

Worth stating plainly, because it decides the size budget. Node tests assert on *structure*:
task counts, hashes, manifest entries, coverage spans. They do not look at pixels, and
`StubImageBackend`'s deterministic placeholder PNGs serve them perfectly and for free.
**Caching mock output would buy nothing** — regenerating a 64×36 PNG costs microseconds.

The cache earns its place in exactly one situation: a fixture that needs **real** art.
That is the record/replay case — exercise the real provider path once, replay it forever,
offline and free. It is what makes the shot timeline's acceptance pass, the PLAY room, and
the FLOOR inspector reviewable by someone who has never held an API key.

### Seam

`ImageBackend` (`packages/providers/src/backend.ts`) — the same seam `StubImageBackend`
implements. A wrapper, so nothing above it changes:

```ts
class CachedImageBackend implements ImageBackend {
  constructor(
    private readonly cache: AssetCache,
    private readonly inner: ImageBackend,
    private readonly opts: { record?: boolean; fixture?: string } = {},
  ) {}

  generate(prompt: string, refs: ImageInput[], params: ImageParams) {
    return this.serve('generate', prompt, refs, params, () => this.inner.generate(...));
  }
  // An edit's base image folds in as its first ref; `op` is what keeps the two apart.
  edit(base: ImageInput, prompt: string, refs: ImageInput[], params: ImageParams) {
    return this.serve('edit', prompt, [base, ...refs], params, () => this.inner.edit(...));
  }
}
```

`requestKey` = `sha256(canonicalJson({ op, prompt, refs: refs.map(r => sha256(r.bytes)), params }))`.
That is deliberately *not* the task hash: the backend never sees a task, and keying on what
determines the image means the cache dedupes across task kinds too. `params` already carries
`modelId` (from `config.models.image`), so a recording cannot be served for a different model.

Two things the sketch above did not anticipate, both shipped:

- **A hit reports the model that made the bytes**, taken from the entry, not `params.modelId`.
  They agree today (the model id is inside the key), but the recording is the authority on its
  own provenance and stamping the caller's id over it would make the manifest lie.
- **`put` refuses placeholder bytes** (`isPlaceholderImage`). Text steps fall back to
  deterministic baselines on any provider failure, so a recording run that quietly degraded
  would otherwise bake mock art into a committed corpus permanently — the same guard
  `imagePart` already applies to references in the Gemini backend.

### The chain constraint

**A cached portrait changes every downstream shot's task hash.** `refs` are upstream asset
hashes, real bytes hash differently from placeholders, and `refs` is part of both the task
identity and the cache key. So:

- A cache recorded from a *complete* run is self-consistent — every link's key matches.
- A cache with a hole degrades honestly: the miss produces a placeholder, and everything
  downstream of it also misses, because its ref hash changed. No silent half-real run.
- You cannot hand-curate "just the pretty ones". It is whole-chain or nothing.

### Size: record at full resolution, and don't pre-pay for a downscaler

The smallest runnable fixture, `SCRIPTS.linear`, is 2 scenes / 1 character / 2 location
variants → `L + 4C + 2N` ≈ **9 assets**. The real run's assets are 1024×1024 lossless PNG
averaging 2.12 MB, so one recording is **~19 MB**.

Against a 5.2 MB `.git` and a 16 MB source tree that is a visible jump, and git history is
append-only so a refresh adds its size again rather than replacing. **It is still the right
trade**, for two reasons:

- **Refreshes are rare, not routine.** A stale entry misses, and a miss is a placeholder —
  suites keep passing. So a cache is re-recorded when someone wants to *look* at real art,
  not every time a prompt rehashes. Five recordings over the project's life is ~95 MB, which
  is an unremarkable repo.
- **Downscaling would defeat the purpose.** The reason to hold real frames is so a human can
  judge character consistency, off-model faces, wrong outfits — the defects the P7 loop
  exists to catch. None of those are legible at thumbnail size, and a cache of art you cannot
  evaluate is worth less than the placeholders it replaced.

Rejected, explicitly, so it does not get re-proposed: **re-encoding recorded assets smaller.**
It needs a PNG *decoder* to pair with the encoder in `packages/providers/src/placeholder.ts` —
five scanline filter types, bit depths, colour types, palette indexing, interlace rejection.
Materially harder than the encoder, and a new class of bug in something that is not the
product, bought for tens of megabytes.

Cheaper levers exist if size ever genuinely bites, in this order: record a smaller fixture;
cache only accepted assets rather than every candidate; and only then consider re-encoding to
WebP (~10× at no resolution loss, but that means a native dependency for the record script).

### Where it lives

`packages/testkit/assets/` — `<key>.<ext>` plus an `index.json` recording, per entry: the
fixture name, the prompt, `params`, the ref keys, the recording model id, and the ISO date.
Provenance, in the same spirit as `manifest.json`.

Testkit-owned, because **nothing may import `@vn/testkit`** — so the cache cannot leak into an
app by accident. The desktop dev app does not need it: it gets real art from `mySampleRepo`,
which is a real run. That split keeps the boundaries rule intact with no exception.

`makeProject({ assets: 'cached' })` opts a fixture in; the default stays placeholder-only, so
existing suites are untouched and the cache can never make a test pass that would otherwise
fail on a machine without it. `assetCacheDir` overrides the directory, which is how the cache's
own tests record into a temp dir instead of the committed corpus.

**`makeProject` never records.** `TestProject.run` always uses mock providers, so a record flag
there could only ever write placeholders — which `put` would refuse anyway. Recording lives on
`CachedImageBackend({ record: true })`, reachable only from the Wave 3 script that runs real
providers.

### Refreshing

`node scripts/record-fixture-assets.mjs [--fixture linear] [--check]`. The logic is
`packages/testkit/src/record.ts` (`recordCorpus`, `checkCorpus`, `formatReport`); the `.mjs`
is a thin driver that bundles it the way `gen-command-catalog.mjs` does, since testkit is
source-only TypeScript. Keeping it in the package means it is typechecked and inside the
boundaries graph rather than being an unlinted script.

**Only the image backend is real.** This was not obvious up front and it is the load-bearing
decision: P5 shot decomposition is an LLM step, so a recording made against a real *text* model
carries shot descriptions no replaying fixture ever asks for again — every image prompt
downstream of it would miss and the corpus would be dead bytes on arrival. So the recorder is
`createMockProviders({ imageBackend: cached })`: mock text and vision pin the run to the
deterministic baseline decomposition, which is exactly what a replay produces. The price is
that a recorded P7 loop is one attempt deep. Replayability and LLM nondeterminism cannot both
be had, and the cache is for real *art*.

That also meant `createProviders` needed no new seam — `createMockProviders` already accepts an
`imageBackend`. The only new surface is `RunOptions.providers` on `TestProject`, whose doc
comment says outright that no test may pass it.

**Staleness is reported, never gated.** A test that failed on a stale cache would block
ordinary work behind a paid re-record — a prompt change is exactly when you least want that.
`--check` is free and offline: it replays the fixture with a placeholder backend behind the
cache and reports reused / missed / orphaned / indexed-but-missing, derived from
`CachedImageBackend.log` (the only place that knows which keys a fixture actually *asks* for;
the cache knows only what it holds). When anything missed, the report says so and marks the
orphan list as suspect — past the first miss the chain constraint re-keys every request, so an
"orphan" there describes the divergence, not a genuinely unused entry.

Measured, not estimated: `linear` issues **9 image requests** end to end (4 in wave 1, 5 after
the gate), matching the `L + 4C + 2N` estimate above.

   `createMockProviders({ imageBackend })` so the stub can be wrapped;
   `makeProject({ assets, assetCacheDir })` + `FIXTURE_ASSET_DIR`. Tested against temp cache
   dirs only — no committed bytes yet.
3. ~~**Record.**~~ **Done.** The corpus is recorded and committed: **9 entries, 11.3 MB** in
   `packages/testkit/assets/`, all from `gemini-2.5-flash-image`. `--check` replays it at
   **reused 9 / missed 0**, which is the whole-chain guarantee holding — every ref's bytes
   matched, so no request downstream of another was re-keyed.

Waves 1 and 2 are independent. Wave 3 is the only one that costs money.

### What the first real run exposed

The script had never been run for real, and two defects only a paid run could surface. Both
are fixed; both were invisible because the report said `corpus 0 entries` and exited 0.

- **The bundle could not resolve `@google/genai`.** The SDKs are `EXTERNAL` and lazy-imported,
  and `@google/genai` is a dependency of `@vn/providers` alone — but the bundle was emitted to
  `packages/testkit/.record-entry.cjs`, from where node cannot resolve it. Every image task
  failed the moment the backend was first touched, so the cache saw **zero** requests. It now
  bundles into `packages/providers/`.
- **The report could not say so.** `RunSummary.ran` is every task that reached a _terminal_
  state, failures included, and the scheduler stores a failure's message only in its log — so
  "wave 1: 3 task(s) done" was three failures. Testkit's `run()` now takes a `logger`,
  `runFixture` collects `task.end` errors into `CorpusReport.failed`, `formatReport` prints
  them, and the script exits non-zero. Staleness is still only ever reported; a _failed task_
  is a different thing and is not reported quietly.
- **`FIXTURE_ASSET_DIR` does not survive bundling.** It is `join(__dirname, '..', 'assets')`,
  correct under jest's per-file CJS transform (`packages/testkit/src` → `packages/testkit/assets`)
  and wrong under any bundle, where esbuild rewrites `__dirname` to the *output* directory. The
  first successful recording therefore wrote a complete corpus to `packages/assets/` — adjacent,
  plausible, and invisible to every fixture. The script now passes `cacheDir` explicitly, and
  `assets.test.ts` pins reachability at the default path (falsified by moving the directory).

**Per-refresh cost.** Nine `gemini-2.5-flash-image` generations, ~$0.039 each ≈ **$0.35** per
full re-record of `linear`. Re-recording is not incremental: a ref's bytes are part of the next
request's key, so changing an early prompt re-keys everything downstream of it and the whole
chain is regenerated.
