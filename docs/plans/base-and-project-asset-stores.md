## What the requirements ask for

Two sentences from [`../designRequirementsEtc.md`](../designRequirementsEtc.md):

- "Assets are separated into **base assets** (such as character descriptions and prompts,
  character model sheets, locations, etc) that are **in their own folder subtree and may
  optionally be in their own git repo**, and **project assets** that are associated with
  specific (**possibly multiple**) scenes or shots."
- "The first assets to be generated are the base ones, e.g. characters, set location
  references."

The ordering half already holds: the P3 gate is a barrier in front of scene rendering, so base
art is generated and approved before a shot is drawn. Nothing in this plan touches it.

## Where the code already is

One flat store. `AssetStore` (`packages/store/src/assetstore.ts`) writes every generated byte to
`vngen/build/assets/<hash>.<ext>` and indexes all of it in one `vngen/build/manifest.json`,
persisted through a single-writer queue. The base/project distinction exists only as data:

- `AssetKind` = `location_ref | portrait | model_sheet | outfit_sheet` (base) vs `shot_image`
  (project) — `packages/types/src/entities.ts:10`.
- `Asset.satisfies` — a single `{ characterId?, outfit?, locationId?, variant?, sceneId?,
  shotId? }` record.

Two facts make the split cheap, and they are worth stating before anything else:

- **The `AssetStore` interface is six methods wide** (`has`, `write`, `read`, `pathOf`,
  `manifest`, `accept` — `packages/types/src/model.ts:52`) and every consumer goes through it:
  the pipeline runners, `@vn/export`, the CLI, the desktop session, testkit. A facade over two
  roots is invisible to all of them.
- **Task identity does not contain a path.** `taskHash(kind, inputs)` hashes the normalized
  prompt, the ordered *ref hashes*, the model id and params. Moving where bytes land cannot
  perturb a single task hash, so no plan here re-generates anything.

## The three problems, stated honestly

**1. One manifest cannot describe two repos.** If `assets/` is to be its own repository —
clonable, shareable between projects, absent in a shallow checkout — then its provenance has to
travel with it. A base asset indexed in `vngen/build/manifest.json` is bytes in one repo with
their meaning in another.

**2. A missing base root must not read as "stale".** The failure that costs real money: a clone
without the asset repo shows an empty base manifest, the planner sees no portrait for any
character, and a run regenerates the entire base library. The store must be able to say
*unavailable* — distinct both from "not generated yet" and from "generated and stale".

**3. `satisfies` is a single record, and content addressing makes that lossy.** Bytes are keyed
by hash; `write` does `index.set(hash, asset)`, so when two tasks produce byte-identical output
the second record **replaces** the first and the first binding is silently gone. Rare with a
generative backend, routine with mocks and fixed seeds — and the requirement asks for the plural
case out loud ("possibly multiple scenes or shots").

## Decisions

**The base root is `<project>/assets/`, beside the authored inputs — not under `vngen/`.**
Decision 3 of the migration report's table. `vngen/` is the generated tree, wiped and rebuilt
conceptually if not in practice; base assets are the opposite — they are approved, referenced by
every later prompt, expensive, and the thing a user would share across projects. Putting them at
the project root is also what makes "their own git repo" expressible at all: `assets/` can be a
repo root, `vngen/build/assets/` cannot without dragging the build tree along.

Layout, mirroring `build/`:

```
assets/manifest.json          the base manifest — provenance travels with the bytes
assets/objects/<hash>.<ext>   base bytes; `objects/` because they are exactly that
vngen/build/manifest.json     unchanged — project (shot) assets
vngen/build/assets/<hash>.<ext>
```

**Routing is by `AssetKind`, and it is the only rule.** The four base kinds write to the base
root; `shot_image` writes to the project root. Not by `satisfies`, not by a flag on the task —
one total function from a kind to a root, so no asset can be ambiguous about where it lives.

**Reads consult both roots, base first.** Hashes are content hashes: a byte present in both
roots *is* the same byte, so the two indices cannot disagree about content. Where they both hold
a record for one hash, **the base record wins** and `manifest()` returns the union deduped that
way. `pathOf` answers from the index that holds the hash, defaulting to the project root for a
hash neither knows (today's behavior, for a caller holding a ref from elsewhere).

**Nothing on disk moves.** An existing project's base assets stay in `vngen/build/manifest.json`
and keep resolving, because the union reads that manifest whole. The split is about **where new
bytes land**, not a migration. No rehash, no re-generation, no `vngen migrate`.

**Three states, not two.** The base root is:

| State | On disk | Meaning |
| --- | --- | --- |
| `absent` | no `assets/` directory | Legacy or brand-new project. Treated as an empty, writable base — the directory is created on first write. |
| `unavailable` | `assets/` exists but has no readable `manifest.json` | Somebody cloned without the base repo / submodule. **Refuse to plan base work**; report it. |
| `ready` | `assets/manifest.json` parses | Normal. |

`unavailable` is the one that must never be confused with "nothing generated yet", and the
distinguishing evidence is exactly what a missing submodule leaves behind: an empty directory.
Project bootstrap creates `assets/` with an empty manifest, so from item 4's `ensureRepo` onward
a project is `ready` from its first commit and `absent` only means legacy. (Not shipped — see
[As shipped](#as-shipped).)

**`satisfies` becomes a list, with a reader shim.** Stored canonically as `satisfies: Binding[]`;
a lone record parses as a one-element list, so every manifest ever written stays readable. `write`
**merges** rather than replaces: a second task binding the same bytes appends its binding instead
of overwriting the first.

**A base repo is a repo like any other.** Item 4 already discovers roots and refuses to commit in
one the project does not own; `Workspace.repos()` gains a `'base'` role and the committer picks it
up with no new policy. Nothing here adds a second commit path.

## Steps

Each step is independently green (`pnpm check`, `pnpm test`, `pnpm lint`).

### 1. `AssetRoot` — one content-addressed root, extracted

Rename today's `AssetStore` body to `AssetRoot`, parameterized by `{ dir, manifest }` instead of
`ProjectPaths`: the write queue, the atomic manifest write, the index, `has`/`read`/`pathOf` all
move across unchanged. `ProjectPaths` gains `baseAssets`, `baseObjects`, `baseAssetFile(hash,
ext)`, `baseManifest`. No behavior change yet — `AssetStore` becomes a one-root facade and every
existing test passes untouched. That is the point of doing it first.

### 2. The two-root facade

`AssetStore.open(paths)` opens both roots and records the base state from the table above.

- `write` routes by kind, creating the base root's directories on demand.
- `has` / `read` / `pathOf` / `accept` consult base then project.
- `manifest()` returns the union, base-first, deduped by hash.
- A new `base` accessor exposes `{ state, root, count }` for the surfaces in step 5 — the
  interface in `@vn/types` gains that one optional member and nothing else.

### 3. `satisfies` as a list

`Asset.satisfies: Binding[]` in `@vn/types` (`Binding` being today's record type, named). The zod
schema accepts either form and normalizes; `AssetStore.write` merges a new binding into an
existing record rather than replacing it. Then the eight read sites — `@vn/export`'s two
predicates, the CLI's portrait filter, the desktop session's two, testkit's one — move from
`a.satisfies.characterId === id` to a `.some(...)`. A helper (`bindsTo(asset, binding)`) keeps
them from each spelling it differently.

### 4. Planning against an unavailable base

The planner already refuses to plan past the gate; it now also refuses to plan base kinds when
`store.base.state === 'unavailable'`, and the run summary says so by name. This is the money
step: it is what turns "regenerate 40 model sheets" into one sentence about a missing checkout.
Tested with a project whose `assets/` is emptied after a run.

### 5. Surfaces

`vngen status` prints base and project asset counts separately, and the base state when it is not
`ready`. The desktop workspace index carries the same three fields so FLOOR can render
"unavailable" instead of an empty gallery. `Workspace.repos()` gains the `'base'` role, which is
all commit-on-save needs.

### 6. Tests

- `@vn/store`: routing by kind; a base byte and a project byte resolving through one facade;
  union manifest with a hash in both roots; the three base states; binding merge on a
  re-written hash; a legacy manifest (base kinds in `build/`) still resolving.
- `@vn/types`: a single-record `satisfies` parsing as a one-element list.
- `@vn/pipeline`: an `unavailable` base plans no base tasks and reports why.
- `@vn/testkit`: `makeProject` runs to the gate and back with the split store — the fidelity
  check that matters, since it goes through the real scheduler.

### 7. Docs

- `docs/asset-stores.md` (new, listed in `docs/index.md`): the two roots, the routing rule, the
  union read, the three base states, the binding list, and what does *not* move.
- `CLAUDE.md` — the project-layout section gains `assets/`; the content-addressed-store core idea
  gains the split in one line; `@vn/store`'s package row names both roots.
- `pipeline-contracts.md` — the asset-store contract restated for two roots.
- `refactorTaskList.md` / `plans/index.md` — status.

## As shipped

The steps above landed as written except in five places, each recorded here rather than edited
into the plan. The as-shipped reference is [`../asset-stores.md`](../asset-stores.md).

**The `unavailable` refusal is total, not base-kinds-only.** Step 4 says the planner "refuses to
plan base kinds". It refuses to plan *anything*: every shot references a location plate and a
portrait, so with the base manifest unreadable those bytes are equally gone and a partial refusal
would plan shots whose references cannot be read — ENOENT in a runner, reported as generation
failures. `baseRefusal(base)` in `@vn/pipeline` is the one sentence; `planTasks` returns `[]`;
`RunSummary.refused` carries it out; `vngen run`, `vngen run --mock` and `vngen cost` print it and
exit non-zero, because a zero-work summary otherwise reads as a finished project.

**`AssetStore.base` is refreshed on write, not a snapshot taken at open.** The first base write
into an `absent` root creates the directory and its manifest, so the root is `ready` from that
moment; a surface reading `base` after a run must not describe the root as it was before. Both
`count` and `state` are updated after a successful base write. (Found by a test asserting
`baseAssetsOf(paths)` and `store.base` agree — they did not.)

**The single-record `satisfies` shim lives in `@vn/store`, not `@vn/types`.** Step 3 sketched the
normalization in a zod schema, but there is no zod schema for `manifest.json` — the store parses
it directly. So `asList` in `assetstore.ts` is where a lone record becomes a one-element list, and
`packages/store/src/tests/assetroots.test.ts` is where a legacy manifest is pinned.

**`AssetStore.base` is optional on the `@vn/types` interface.** Declared `readonly base?:
BaseAssets` so an in-memory fake — the object literal `@vn/export`'s test uses as a store — still
satisfies the interface without inventing a base root it does not have.

**Bootstrap does not pre-create `assets/`.** The decisions section says project bootstrap should
create the root with an empty manifest so `absent` would only ever mean legacy. It does not, and
should not: `ensureRepo` runs when the desktop app *opens* a workspace, and writing a file into
the user's project as a side effect of opening it is a bigger act than the state it would tidy
away. `absent` is already the safe state — writable, and flipped to `ready` by the first base
write — so pre-creating the root buys nothing. The CLI has no bootstrap at all, so the line could
not have held there in any case.

## Out of scope

- **Moving existing bytes.** A project that wants its base assets in the new root can copy them;
  nothing in the app will do it silently.
- **Sharing a base library between projects.** The layout makes it possible (it is a repo); the
  app gains no UI, config key, or path indirection for it here.
- **Base assets as *authored* files.** Everything in `assets/` is still generated art with
  provenance. Hand-drawn reference images stay where they are (`characters/<id>/refs/`).
- **A third root for outfits.** Outfit sheets are a base kind and land in the base root; item 6
  decides what an outfit *is*, not where its bytes live.
- **Garbage collection.** Neither root prunes unreferenced bytes today, and this plan does not
  start.
